# Learning guide structure

Adapt sections to the repository and requested format; omit sections that do not help the learner.

1. **Five-minute orientation:** project purpose, inputs/outputs, runtime or training loop, and a small current-system map.
2. **History map:** time-ordered phases derived from actual commits, each with the problem, decisive change, evidence, and outcome. Show branches or abandoned routes where relevant.
3. **Turning-point cards:** before/after code path; what changed and why (label inference); validation; later fate; trade-off; exact SHA/path links.
4. **Learning path:** prerequisite concept → specific code and commit → simple exercise → self-check. Order from whole system to mechanism to optimization. Explain unfamiliar terms at first use.
5. **Evidence ledger:** scoped refs and date, inventory count, inspected patches, relevant tests/logs/issues, evidence gaps, and confidence limits.
6. **Next action:** one concrete reading or reproduction step that best reduces the learner's current uncertainty.

For a focused feature request, make the feature timeline primary and keep the whole-system map brief. For an own-project retrospective, include failed experiments and what would falsify the lessons. For comparisons across versions, distinguish code evidence from benchmark or deployment evidence.
